Reporting for Boeing S1000Dmanager

Overview

Boeing S1000Dmanager is a document management tool that supports sending technical documents (like aircraft maintenance documentation) through workflows as they are authored so they can be quality checked and then published. These documents are grouped by project and can number in the thousands.

Managers who oversee these projects complete weekly reports to check on the status of document changes from their charges. These managers take the data and send it upstream to their managers to report on the health of the project’s authoring.

Previously, this had been a fixed set of reports. When requesting new reports, managers had to come to the S1000D product team to get new reports or use a technical scripting software to retrieve the data out of the database.

With this update, reports were updated so that these managers could have a more flexible set of reports. Instead of fixed reports with fixed data queries, they could make reports on their own through the UI, which allowed them to select any fields in the database they needed as well as run excel like functions against that data (e.g. “Column B” is the result of if “Column A” is greater than 5 and if so, reads out “TRUE”).

Analysis

The initial request was for 10 new xml reports. I know from past conversations with our users that this is an ongoing problem where they have to keep requesting new reports from us since reports are hard coded into the system.

We were given 10 sample XML reports they wanted the application to provide, so I worked with a developer to examine commonalities between these reports.

Additionally, I took a few questions to the managers using our application, along the lines of:

  • Why these reports?
  • How often are they run?
  • Who runs them?
  • Do you have other reports you need to run?
  • What are you trying to do with the data?

User Flow Diagram

The user flow diagram lists out each state of the report creation process.

The path can start from the Inbox screen (a list of all documents the user owns) to make use of the filters provided already.

It can also start from the Reporting screen if they have a report they want to start from or have a specific document list in mind.

Mockups

Following the user flow diagram, I set up the screens and added elements from the design library that suited the data type I needed to display.

After feedback, the initial set up screen I had was kept for editing a report, but I moved to a ‘walk through’ wizard for the report creation to help step them through all the pieces they’d be required to verify and set. This would prevent an invalid report from being saved.
