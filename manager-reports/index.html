Overview

The addition of an upgraded reporting screen allows project managers to complete various types of reports on the status of documents in the system.

Role/Responsibility

UI Designer & Front End Developer

Users

Project managers

Scope

  • Add the ability to create 10 new reports
  • Remove old reporting screen and dashboard technical debt

Constraints

Time boxed (4mo)

Results

As far as user metrics, just shipped so somewhat TBD.

Added capability for multiple kinds of reports, diminishing the need for future static report requests, saving time and effort for both the product team and product managers using the system.

Analysis

With the initial request we were given 10 sample XML reports they wanted the application to provide. Working with a developer, we examined commonalities between these reports and discussed various ways of implementing them in the application.

I also took a look at previous bugs, requests, and feedback. We’ve gotten complaints before about not having the ability for managers to document status out of the application. They use this to create status reports on the project to their managers.

A few questions I took to our program liaisons (people who work directly with our customers and know their problems) and authors were along the lines of:

  • Why these reports?
  • How often are they run?
  • Who runs them?
  • Do you have other reports you need to run?
  • What are you trying to do with the data?
  • Is there anything the current reports give you trouble with or you don’t like?
  • Is there anything about the current reports you do like?

Mockups

I started by recreating the old Reporting screen with the same elements in the new design system. The previous Reporting screen was in legacy code and didn’t use it. While there were a couple of bugs we’d need to fix in development, there weren’t a lot of issues with the function of it. The form needed to be fixed, and I needed to add a few additional features.

From there, I started with a flow diagram of how I wanted things to work. In essence:

Inbox (documents list) -> report type selection -> set up report -> save report -> run report

I used a trigger from the Inbox in order to utilize the documents list and features. They wanted a list of documents as part of the report and the documents list provided something they were familiar with. They could use that to set up which documents they wanted.

After the set up and trigger, I started working with our design system and selection. We had a component for that: a card list. It provided quick access to the reports we’d offer (there weren't many) and allowed for descriptions. This feature was new and some guidance was necessary.

For the set up, I went again to the component library. We had a vertical tabs menu that worked well for sets of screens. The rest was ordering the fields in a logical way.

After feedback and revisions, the initial set up screen I had was kept for editing a report, but I moved to a ‘walk through’ wizard for the report creation to help step them through all the pieces they’d be required to verify and set. This would prevent an invalid report from being saved.

Reflection

Looking back, I’d like to have included more focus groups earlier on. There was one in the initial information gathering phase and one towards the end of the mockup phase. I think a couple more discussions with users in the beginning mockup stages would have been beneficial.

Something else to consider is the report creation wizard. I’d like to get more feedback on how the flow is working out, especially for those that don’t need as much hand holding. Skipping right from the initial details screen to saving and running the report in fewer clicks.
